## Direction we follow (SOURCE: Omarchy M team decisions and chat, Sep–Nov 2026)

- Integrate into the main omacom repositories wherever practical: omacom/omarchy, omacom/omarchy-pkgs, omacom/omarchy-mac-pkgs, omacom/linux-aurora, omacom/m1n1.
- **The kernel work for M4, M5 and M6 is merged together with Linux 7.3.** Our kernel series now applies to aurora-silicon/linux `integration/aurora` 7.3.0 (local 1.902, installed 2026-11-13; rebased onto Aurora's tip `abd6d4a09ffe` in 1.870, on Aurora's newer tip `da8e1acf3656` since 1.877) for that merge, rather than being sent as a separate J604 tree.
- **CPU power profiles come from stock Omarchy.** Since 1.877 the kernel registers the CLPC's platform profile; the stock `omarchy-power-profiles-daemon` 0.30-8 (omacom/omarchy-pkgs#2381) drives it, installed unchanged from the edge channel with kernel 1.879. Nothing is carried for it.
- Results are reported through [omarchy-m-testing.org](https://omarchy-m-testing.org), one result per check. "Not tested" is the default; an implementation alone is not a pass.

## How we work

- **Stock userland, edge channel.** The J604 runs stock Omarchy edge. The only Omarchy changes we carry are the keyboard-backlight series and the built-in panel defaults; everything else we carry is hardware enablement (see `STATUS.md`).
- **One topic per pull request**, small and reviewable, against each repository's default branch and rules.
- **Every pull request and issue is opened under Dylan's name**, with his sign-off where the project asks for one.
- **Credit.** Work that is someone else's (much of the kernel series we carry) is never sent as ours. Where we build on it, we credit it and coordinate with its author. Where someone already has an open pull request for the same thing, we test theirs instead of sending a second one.

## Overlap with work already upstream (SOURCE, checked 2026-11-08)

The Aurora kernel (aurora-silicon/linux) has merged DjDeveloperr's J604 / M4 device trees: #1142 (J604 and M4 trees) and follow-ups (#1166 new M4 file layout, #1170/#1171 M4 GPUs on by default, #1178/#1179/#1207 J604 display enable and panel). Also related: Ryan's #1035 (M4 CPU DVFS; closed without merging), aeries0x's #1186 (J604 power-manager policy and boot framebuffer; merged 2026-11-09), and Eryk's J713 work (camera, USB4 routers, external display, audio with Erik).

What that means for us:
- Our base J604 enablement (SMC, storage, keyboard and trackpad, Wi-Fi/BT, USB2, GPU and display resources) largely duplicates #1142, so **we do not send it**; we rebase onto Aurora's tree and send only what goes beyond it.
- What is only in ours (MEASURED offline 2026-11-08, our J604 device tree against Aurora's): speakers, ANE and AVD nodes, AOP sensors (ambient light, lid angle, accelerometer, gyroscope), CPU performance controllers and PMU, the display crossbar, sleep power-manager nodes, the USB4 routers and the SD reader. Aurora already has the drivers and bindings for most of that, so most of it is device-tree work on Aurora's layout.
- #1035 (cpufreq/cpuidle) was closed without merging, and #1186 (power-manager policy, boot framebuffer) merged on 2026-11-09 (SOURCE 2026-11-10). We have not posted test results for either; our series still has to be compared with #1186 (TO-VERIFY).
- Our display work must be compared with #1178/#1179/#1207 first; only the remaining delta goes out.

**Where kernel changes go:** SoC- and board-level changes go to aurora-silicon/linux first, coordinated with DjDeveloperr and Eryk; omacom/linux-aurora receives them at its 7.3 merge. A change that only matters to Omarchy's packaging of the kernel goes to omacom/linux-aurora directly. We confirm this split with the kernel maintainers before the first kernel pull request (TO-VERIFY).

## Notes for upstream (found 2026-11-09; nothing posted)

Findings from moving the J604 to the Aurora 7.3 kernel base. Each is a note to raise with the owners, with Dylan's sign-off; none is a J604-only problem.

- **(a) omacom `libfprint-git` and the version 5 Secure Enclave interface.** omacom/omarchy-pkgs `libfprint-git` -5 (`dd8988f747`) accepts only interface version 4. The 7.3 base moves it to 5 (aurora-silicon/linux f70f1acd35; aurora-silicon/linux#660, which proposed holding it back until the userspace shipped, was closed without merging). On such a kernel fprintd ignores the sensor and Touch ID is lost (MEASURED 2026-11-09). The fix exists upstream: aurora-silicon/alarm-aurora#56 and aurora-silicon/aurora-sep-userspace#3 (both merged 2026-10-31). We carry their 0004 + 0005 as `libfprint-git` 5.604. A later official -6 without them would replace ours and lose Touch ID again on 7.3.
- **(b) boot.bin size with the 7.3 device trees.** The 7.3 kernel package ships 137 DTBs (1.617: 115). `update-m1n1`'s default takes all of them, and the resulting boot.bin (13,576,387 B) did not boot: m1n1 stage 1 (1.608) refused it and stopped in its proxy (MEASURED 2026-11-09). The largest image measured to boot on the J604 is 10,492,247 B; the image parses correctly, so size is the cause, and the exact chainload check that refused it is INFERENCE. A J604-only DTB selection gives about 4.7 MB; the J604 has booted such an image (m1n1 1.608 + the 1.703 J604 DTB + U-Boot, 4,700,171 B) since 2026-11-09 (MEASURED 2026-11-09). Where the fix belongs (the DTB selection in the boot package, or the stage-1 chainload limit in m1n1) is for the owners to decide. Our boot package now selects the machine's own device tree: `omarchy-mac-boot` 1.616's `/etc/default/update-m1n1` sets `DTBS` to the one device tree of the newest kernel whose first compatible is the running Mac's, only when exactly one matches, and otherwise keeps `update-m1n1`'s default (CODE). Three machines in the 7.3 set have two device trees with the same first compatible (t8122-j613 and -25g83, t8122-j615 and -25g83, t6040-j616s and -tether; MEASURED 2026-11-09), so a rule by file name would be wrong there; counting falls back to the default. Upstream's recipe has `dtc` only in `checkdepends`; the selection needs `fdtget` on every Mac, so our build adds `dtc` to `depends` (SOURCE, CODE). In m1n1's `chainload_image()` stage 1 refuses an image whose copy would run into its live heap; we only measured that the limit on the J604 lies between 10.49 MB (boots) and 13.58 MB (refused), and did not check other SoCs (CODE, MEASURED 2026-11-09). A side note: `omarchy-mac-retire-saved-modules` reads `/etc/default/update-m1n1` without `OMARCHY_DTB_OVERLAYS=0`, so on a Mac where an `omarchy-ane` overlay applies it may exit early and never retire saved modules (INFERENCE, from the code; not reproduced).
- **(c) Aurora `t8132-platform-handoff` on the J604.** It logs "cannot resolve PMGR policy for /soc/power-management@380780000: -1" and stops before changing anything: the J604 tree has a PMGR node (`pmgr_cio`, from `t8132-usb4.dtsi`) that its embedded platform data lacks (CODE, MEASURED 2026-11-09). Harmless today: the result equals 1.617, which had no handoff; the same line appears with the 7.3 J604 device tree on 1.703 (MEASURED 2026-11-09). We do not skip the node, because that would apply the J713's PMGR policy to the J604 without J604 proof.
- **(d) omacom `mesa-aurora` and the "aurora" DRM driver name.** The 7.3 base names the GPU's DRM driver "aurora" (aurora-silicon/linux a97f7b8be0). omacom/omarchy-pkgs `mesa-aurora` pins omacom/mesa `a19691114759`, which recognises only "asahi"; the fix is aurora-silicon/mesa 6edf62bcfd0 ("asahi: accept the aurora kernel driver name", SOURCE). With the old Mesa, GL falls back to software and Vulkan finds no device (INFERENCE, from the code); on the J604 the 7.3 kernel with Mesa 1.8132 starts no Hyprland session (MEASURED 2026-11-09). Our Mesa build carries 6edf62bcfd0 (on aurora-silicon/mesa `aurora-wip`) as local 1.8133, installed 2026-11-09; with it the Hyprland session starts on the 7.3 kernel and OpenGL and Vulkan report the Apple M4 GPU, not llvmpipe (MEASURED 2026-11-09).
- **(e) omacom `libva-v4l2_request-avd` and the "aurora" DRM driver name.** libva picks its driver from the render node's DRM driver name, so on a 7.3-base kernel it looks for `aurora_drv_video.so`; omacom/omarchy-pkgs `libva-v4l2_request-avd` -1 (`08b5d28a67`) ships only the `asahi_drv_video.so` alias, so VA-API does not load and players decode in software (MEASURED 2026-11-09). The fix is upstream as aurora-silicon/alarm-aurora aedcf240ca91 (Ryan Murray) and open for omacom as omacom/omarchy-pkgs#2375 (pkgrel 2) (SOURCE). We built the same alias as local 1.604 and installed it on 2026-11-09. On this M4 with the 7.3 kernel it exposes a GPU fault: stock mpv's zero-copy path showed an empty window at 1080p for H.264, HEVC and VP9 (3 of 3 runs each; 4K H.264 correct), with `VK_ERROR_DEVICE_LOST` and a kernel GPU submit error (`EFAULT`) (MEASURED 2026-11-09), while the copy path (`vaapi-copy`) decoded all three correctly (MEASURED 2026-11-09). We rolled it back to the official -1 the same day. #2375's official -2 adds the same alias, so on a kernel without that fix it would expose the same fault here (INFERENCE 2026-11-09). The cause is a kernel bug, fixed in our kernel 1.704 (patch 0164, note (g)). With 1.704 we carry the alias again as local 1.604, and stock mpv decodes in hardware with the correct picture (MEASURED 2026-11-09); the official -2 sorts above it and replaces it.
- **(f) GPU module options under the old name.** With the module renamed `aurora` (aurora-silicon/linux a97f7b8be0), `options asahi ...` in modprobe.d no longer reaches the module when udev loads it at boot: kmod applies an option only under the module's real name or the name it was requested by (MEASURED 2026-11-09 with kmod's modprobe on the J604, against a private config; CODE in kmod). The same rule covers `asahi.<param>=` on the kernel command line (CODE). `options aurora ...` / `aurora.<param>=` work. aurora-silicon/linux `Documentation/ABI/testing/sysfs-driver-asahi-agx-stats` still names `asahi.stats_export` (SOURCE). Nothing on the J604 uses either today.
- **(g) GPUVM exec lock and a shared reservation (aurora-silicon/linux).** The Rust `GpuVm::exec_lock()` runs `drm_gpuvm_exec_lock()` with flags 0. A client that closes its handle to an imported dma-buf and imports the same dma-buf again gets a second GEM object, while the first keeps its GPU mappings until the VM's in-flight jobs retire (handle-close cleanup is deferred); both share one reservation, `drm_exec` meets it twice, ww_mutex returns -EALREADY, and without `DRM_EXEC_IGNORE_DUPLICATES` the error is passed up (CODE). On G16 every submission reads its command streams under this lock and the stream gate turns the error into EFAULT, so mpv's zero-copy VA-API into Vulkan got `VK_ERROR_DEVICE_LOST` and a blank 1080p picture (MEASURED 2026-11-09 on 1.703, ioctl trace of mpv). The idle-VM restore path takes the same lock (CODE). Our patch 0164 sets `DRM_EXEC_IGNORE_DUPLICATES`, as nouveau, panthor, xe, msm and imagination do (CODE). The same code is in 1.617, and upstream `integration/aurora` `d7303c39e215` still has it (SOURCE, 2026-11-09). With 0164 (our 1.704), the same mpv test runs with no submit error (MEASURED 2026-11-09). Sent as aurora-silicon/linux#1392 (open, not merged); Wave 2 #22.
