# J604 bring-up status (MacBook Pro 14-inch, M4, 2024)

Board `apple,j604`, SoC `apple,t8132` (M4, 4 performance + 6 efficiency cores, 10-core GPU, 16 GB). Last updated 2026-11-09.

## How to read this page

- **Working**: measured on this Mac, with the date of the measurement.
- **In progress**: code exists (in our kernel, boot loader or packages) or part of it runs, but the block is not yet measured working end to end.
- **Not started**: no code yet.
- Every row carries an evidence label and a date:
  - **MEASURED** (date): run on this Mac.
  - **INFERENCE** (date): our reasoning, not a measurement.
  - **TO-VERIFY** (date): open question, or a claim not yet checked on the current build.
- A driver that loads, or a device that appears, is not a pass on its own. Where that is all we know, the row says so.
- "Current build" means the packages listed below, installed on 2026-11-09.

### CPU
- **Working.** MEASURED 2026-11-09: 10 cores online; `apple-cpufreq` maximums 4464 MHz (performance) and 2892 MHz (efficiency); `apple_idle` cpuidle.
- Frequency reporting: **fixed in 1.723** (0219): the reported frequency (`cpuinfo_cur_freq`) is now the reached state; one busy performance thread shows 3984 MHz while 4464 MHz is requested (MEASURED 2026-11-10 on 1.723). Before 1.723 `scaling_cur_freq` showed the requested state, not the one reached. On 1.704 a performance core delivered about 3.93 GHz while 4.464 GHz was reported, and 1.717 reports the same way (MEASURED 2026-11-09/10). CODE: the driver's T8132 entry has no mask for the reached-state field, so it reports the requested one. Since 1.721 (0215) `dvfs_registers` shows the raw command and status words, so the status layout can be worked out on the machine; the reported frequency is unchanged (CODE).

- Suspend (s2idle): **Working on 1.710 to 1.734, on 1.736, 1.800, 1.802, 1.803, 1.804, 1.805, 1.807, 1.808, 1.809, 1.810, 1.811, 1.813, 1.816, 1.820, 1.821, 1.823, 1.826, 1.829, 1.832, 1.833, 1.836, 1.841, 1.843, 1.844 and 1.845** (MEASURED 2026-11-10, on each: `rtcwake -m freeze -s 8` returns, the journal shows suspend entry and exit, nothing refused, the desktop is alive). From 1.710 to 1.720 each cycle also logged a resume failure for both external display controllers (`Retained DCP session quarantined: -62`, then `PM: failed to resume: error -62`); the internal panel's controller was not affected (MEASURED 2026-11-10). - Deep sleep (suspend to RAM): **In progress, not working.** From 1.705 to 1.811 the kernel offered it (`[s2idle] deep`, MEASURED 2026-11-09); since 1.813 it is not offered on the J604 (see the end of this item); the boot firmware already publishes what it needs (no m1n1 change). Suspend-to-idle stays the default, so closing the lid behaves as before. 1.710 adds the GPU firmware stop and warm restart a full deep sleep needs, behind a switch that is off by default (0181). The first full suspend-to-RAM trial, on 1.710 with that switch on, FAILED: the machine went down and came back with a cold boot about 10 s after the wake alarm, so the wake did not reach the kernel; no hang, no power cycle needed (MEASURED 2026-11-10). No log of the attempt survived, so where it stopped is not known yet (TO-VERIFY). Three more trials on 1.722-1.724, with m1n1 1.610 told to hold in its warm path and with the wake alarm 25 s to 120 s away, FAILED the same way. In all four trials the kernel started again 36-46 s after the suspend began (a cold boot takes about 10-15 s), also when the alarm was still 75 s away, and never late enough for a warm-path hold to have run (MEASURED 2026-11-10). So the sleep entry itself does not complete, and something resets the machine about 30 s later. A fifth trial on 1.724, with the processor spinning instead of taking its final power-down step and a 90 s kernel watchdog, was reset at the same time (MEASURED 2026-11-10), so the reset does not come from the application processor. On 1.728 the kernel's suspend test mode located the stage: deep sleep stopped right after the device suspend stage, before any late suspend step, the GPU firmware stop or the final power-down, still reset the machine, while deep sleep stopped after freezing tasks, and the device suspend stage on the suspend-to-idle path, both came back (MEASURED 2026-11-10 on 1.728). On 1.729 the same test with the stop held 90 s instead of 45 s moved the reset 46 s later, so it is not a fixed timer from the start of the suspend: it is armed when the device suspend stage resumes and fires about 30-35 s later (MEASURED 2026-11-10 on 1.729). On 1.731 and 1.732, test switches that leave out the system controller's sleep warning or the display controllers' firmware power-down did not change it: the reset came at the same time (MEASURED 2026-11-10 on 1.731 and 1.732). Every reset in these trials left the same boot record, "PMU logged 1 boot error(s) and 0 panic(s)", and no panic or watchdog line, and nothing on the Linux side can reset the machine here (no runtime watchdog, `kernel.panic=0`), so the reset comes from outside the kernel: the system controller, the power manager or a coprocessor (MEASURED and CODE, 2026-11-10); which one is not known yet (TO-VERIFY). So the reset is set off by work that only suspend-to-RAM does in the device suspend stage, not by the missing power-down steps. On 1.733 and 1.734 test switches named that work: with the Secure Enclave's sleep request left out (`apple_sep.debug_skip_sleep_request`) the same test came back without a reset, once together with the storage controller's sleep stop (1.733) and twice alone (1.734), while all 10 test runs without that switch reset, the kernel starting again 91-93 s after the start, and leaving out only the storage controller's sleep stop still reset (MEASURED 2026-11-10 on 1.733 and 1.734). The reason in the code: the J604's Secure Enclave node lists no power domain, so the kernel sent the enclave's sleep request already in the device suspend step instead of at the last refusal point of the sleep driver, just before the power-down (CODE). 1.736 fixes that (0242): the same test with no switch at all came back on the same boot 163 s after the start, with no reset (MEASURED 2026-11-10 on 1.736, one run). A full suspend-to-RAM (`rtcwake -m mem`, GPU switch on, enclave request left out) no longer reset either: the power-management coprocessor refused it at the late suspend step because the GPU's vote there has no release message, and the GPU firmware, already stopped for the sleep, did not come back, so the GPU stayed lost until a reboot (MEASURED 2026-11-10 on 1.734). Those two GPU items are what still stands between the J604 and a working suspend-to-RAM (TO-VERIFY: how macOS drops that vote). Since 1.803 the kernel has a change for each (0229-0230, both only with `aurora.g16_deep_sleep=1`, off by default). The first real suspend-to-RAM with them on 1.804 (`rtcwake -m mem`, every test switch off) HUNG: no return within 7 minutes and no reset, so the machine needed the power button; the journal of that boot ends at the start of the trial, so where it stopped is not known (MEASURED 2026-11-10). 0237 (1.807) adds a switch meant to let a later test reset itself instead of hanging. A second test on 1.807 hung as well: a suspend-to-RAM told to stop at the start of the sleep driver's last step, before any power-down (`apple_s2r.abort_before=1`), with 0237's watchdog on (`apple_s2r.wdt_from_enter=1`, `apple_s2r.wdt_timeout=120`), never came back and did not reset within about 5 minutes, so the machine needed a forced power-off; the journal of that boot ends when the test started (MEASURED 2026-11-10 on 1.807). A code review then found a concrete defect: a run told to stop there still sent the Secure Enclave its real sleep request before it stopped (CODE). Since 1.809 (0241) such a run sends no request; the staged tests below found a second stop in resume, and its guard is in 1.811 (0247, off by default). An awake test on 1.808 showed that the SoC watchdog can reset the machine: with a 15 s timeout and no keepalive it reset 15-20 s later (MEASURED 2026-11-10). By code, the sleep driver put the watchdog back to its old setting as the first step of resume, so a stop later in resume had no watchdog (CODE); 0242 (1.809) keeps it armed through resume. Staged tests on 1.810 and 1.811 (MEASURED 2026-11-10) each ran a suspend-to-RAM through the sleep driver's last step and stopped it at the start of that step, before any power-down, with the breadcrumb and the bring-up watchdog on. Without the enclave's sleep request (1.810) the machine came back in about 1 s with the full breadcrumb trail. With the request sent (0246), the 1.807 hang came back: the machine stopped in resume (last breadcrumb step 0x39, after the system-core resume and before the end of the early device resume), and the bring-up watchdog reset it about 120 s later, with no power-button press. The enclave's DART has no sleep list in the device tree, so its own resume reads registers that are not powered back after the enclave went to sleep (CODE). With the 0247 guard on (`apple_dart.sleep_save_unlisted=1`) as the only change, the same test came back in about 1 s with the full trail (1.811). After a stopped run that sent the request, the enclave stays asleep until a reboot, by design. No real power-down has been completed yet, and the guard and the other bring-up switches stay off by default. Real suspend-to-RAM is not working; deep sleep stays off by default and suspend-to-idle is the shipped sleep, which passes the boot gate of every build. Why it cannot work yet (CODE, 2026-11-10): the sleep driver follows the T6020 design. Its CPU complex state save has no CPU complex described in the J604 device tree to work on, and on T8132 it has no sleep commit step and no sourced cluster layout, so it cannot commit a sleep there. The 1.804 hang most likely stopped at that same point after the enclave's sleep request and then stalled in resume like the 1.807 test (INFERENCE); the 1.807 hang's cause is measured and guarded (above). Since 1.813 (0248) the driver checks this before it offers `deep`: on the J604 `mem_sleep` lists only `[s2idle]` and a request for `deep` is refused at once (MEASURED 2026-11-10 on 1.813). The way forward is the T8132 suspend-to-RAM sequence that Aurora traced from macOS on the same SoC and published in open aurora-silicon/linux pull requests (SOURCE; it slept on an M4 MacBook Air, not yet on the J604). Porting it is in progress. 1.816 adds three pieces for it, inert at the defaults: a test switch to start a core that was powered down alone again, a read-only log of the T8132 sleep words, and the six macOS wake sources in the J604 device tree (0250-0252); `deep` is still not offered (MEASURED 2026-11-10 on 1.816). 1.821 carries the ported sequence (0265-0269) behind `apple_s2r.t8132_sequence`, off by default, together with Aurora's GPU and power-manager deep-sleep path (0270-0276); `deep` is still not offered and a real sleep is still refused (MEASURED 2026-11-11 on 1.821). Staged tests (MEASURED 2026-11-11): on 1.821, with `apple_s2r.t8132_sequence` set for one boot, `deep` was offered with no mapping errors, and runs that stop the sequence at chosen steps before the sleep's commit came back with no error lines, all 10 CPUs online and the power words unchanged. On 1.823 a run that goes up to the commit was refused before the sequence started: the SSD controller and its PCIe block are still on, and lowering them is not ported yet (m1n1 1.611 now publishes the tables that step needs). In that run one before/after comparison of the power-domain list differed; that item is still open. 1.829 adds the lowering and raising of that block (0284-0287). The first real T8132 sleep ran on 1.829 with the sequence set for one boot (MEASURED 2026-11-11): `rtcwake -m mem` never returned, and the machine reset itself and started again 139 s after the sleep began. 1.833 adds step markers past the sleep's match and a separate time for each watchdog (0296-0297, off by default). With them (MEASURED 2026-11-11 on 1.833, the sequence set for one boot each time): a staged run that stops before the lowering of the SSD controller's PCIe block returns; one that lowers and raises the block and then stops, with no sleep, does not return, and the machine resets itself about 130 s after the run began. A trace of the power domains in a run that returned shows three of that block's domains powered off by the kernel at the last stage of the device suspend, while the SSD controller still runs, and on again in the resume. The boot firmware does not keep the step markers past the match, so they could not name the step. 1.836 makes the block's PCIe host hold those domains through a T8132 sleep (0301-0302), refuses a sleep whose lowering fails, gives each step its own watchdog time, and keeps the kernel console in a ramoops region across a reset (0298-0300, 0303); on the J604 the ramoops region kept nothing across the resets below (MEASURED 2026-11-11). On 1.836 a staged run that stops only the SSD controller and then undoes it, with no sleep, did not return, and no watchdog reset the machine in more than 9 minutes; it was switched off by hand. 1.841 (0304-0311) adds watchdog cover for the whole suspend. The same run on 1.841 did not return either, and the machine reset itself 350 s after the call, not at the 120 s of the watchdog armed for the sleep (MEASURED 2026-11-11; the cause is being worked out). On both kernels the watchdog of an awake machine resets it at the programmed time (MEASURED 2026-11-11). Deep sleep is not working; suspend-to-idle is the only sleep state. 1.808 adds the 0238 breadcrumb, off by default, so a later test that hangs can leave its last step behind, and 1.809 (0244) adds steps for an abort, the start of resume and the end of a sleep. After the watchdog test the next boot reported the boot stage byte as a failed-boot stage together with the firmware's boot error count, so the breadcrumb survives a watchdog reset (MEASURED 2026-11-10 on 1.808); whether it survives a forced power-off is not known (TO-VERIFY). With the default settings none of this happens: the 0181 switch (`g16_deep_sleep`) is off, so choosing `deep` makes the GPU driver refuse at the prepare step, the system carries on and nothing resets (MEASURED 2026-11-10 on 1.725).

### Touch ID
- **Working.** MEASURED 2026-11-09: used for sudo, polkit and the lock screen.
- Carried by: kernel series (Secure Enclave sensor node; on 1.703 the sensor runs in SPI mode 1), two `omarchy-mac` changes (stock lists the J604 as not eligible; since 2.17, patch 0006, the start-up race below), and `libfprint-git` 5.604.
- **Start-up race, fixed in `omarchy-mac` 2.17 (installed 2026-11-11).** `/dev/sep-bio` takes one opener at a time. On one boot fprintd started while `omarchy-mac-touchid-activate` still held the node: fprintd logged "cannot open /dev/sep-bio: Device or resource busy", dropped the reader and answered "No devices" for about 30 s, until it exited idle (MEASURED 2026-11-11, journal). The EBUSY line is on 1 of the 70 kept boots (MEASURED). Two causes (CODE): only the udev rule queued the activation, and fprintd's drop-in ordered it `After=` a job that might not exist yet; and the activation reported ready from the driver attributes while the driver could still hold the session. 2.17 makes fprintd want the activation (so the order always holds) and reports ready only once a second opener would get the node (bounded at 10 s; on timeout it fails with a journal line instead of passing silently). After the install on 1.836 (MEASURED 2026-11-11): the activation finished with status ready, 0 race lines, fprintd lists the sensor, and a verify starts (stopped after 4 s, no finger). On the first boot with 2.17 (kernel 1.841, MEASURED 2026-11-11): the activation finished during that boot with status ready, fprintd logged 0 race lines and lists the sensor, and a verify starts. That is one boot; the race was on 1 of 70 boots, so one clean boot does not yet show it is gone (INFERENCE). Kernel 1.843 adds the kernel half (0320): an open that arrives while the activation's own open still holds the node now waits for it (at most 5 s) instead of being refused (CODE). On 1.843 (MEASURED 2026-11-11) the activation finished with status ready, fprintd lists the sensor, a verify starts, and the wait never ran out.
- The 7.3 kernel base moves the Secure Enclave biometric interface from version 4 to 5 (SOURCE: aurora-silicon/linux f70f1acd35). Stock `libfprint-git` -5 accepts only version 4, so on a 7.3 kernel fprintd ignores the sensor ("interface version 5, expected 4"; MEASURED 2026-11-09). `libfprint-git` 5.604 (installed 2026-11-09) accepts 4 and 5; with it fprintd finds the sensor on the 7.3 kernel (MEASURED 2026-11-09), and Touch ID for sudo works there by the owner's check on 1.702 (MEASURED 2026-11-09). The prints enrolled before the move still match (INFERENCE 2026-11-09: no new enrolment was made).

With the 1.823 device tree it held 4,704,706 bytes (MEASURED 2026-11-11 on 1.823 with m1n1 1.611); with m1n1 1.610 the 1.823 and 1.821 device trees gave the same size, the 1.820 device tree gave 4,704,236 bytes, the 1.816 device tree gave 4,704,160 bytes, the 1.813 device tree gave 4,704,236 bytes, the 1.805 to 1.811 device tree gave 4,704,196 bytes, the 1.800 to 1.804 device tree gave 4,702,008 bytes, as did the 1.734 to 1.736 one with its nodes in another order; the 1.727 to 1.733 device tree gave 4,701,856 bytes, the 1.720 to 1.726 one 4,700,239 bytes.

A port is published whole or not at all, and the host's and port 0's tables are exported as before. On the J604 the SD reader's port now carries its own four tables, and the quick boot gate and the earlier boot-chain checks pass (MEASURED 2026-11-11 on 1.833).
- m1n1 1.610 (installed 2026-11-10 with kernel 1.722) is 1.608 plus 0038: bring-up hold points with the watchdog armed, which the suspend-to-RAM driver can request (kernel 0213) to find where a deep-sleep wake stops; they do nothing unless requested (CODE). ## Known differences from stock Omarchy on this Mac

1. **mpv hardware decode default never lands** (all Apple Silicon Macs): `omarchy-settings` owns `/etc/mpv/mpv.conf`, so `omarchy-mac`'s Apple default is never installed (MEASURED 2026-11-09). Issue: omacom/omarchy#18229.
2. **kyber fails on two NVMe namespaces with Linux 7.2** (MEASURED 2026-11-09; not rechecked on 7.3). Fix: omacom/omarchy#18228.
3. **Touch ID not offered by stock `omarchy-mac`** on the T8132. We carry a two-line change.
4. **Unlock prompt can go black while typing** with stock Plymouth on device-tree Macs. We carry a small Plymouth patch.
5. **Glassy bar at about 59 fps** on this 120 Hz panel with stock (MEASURED 2026-11-09). 119 fps needs omacom/omarchy#18176. Re-measured on 1.731: still 59 (MEASURED 2026-11-10).
6. **CPU power profile on AC.** The edge `omarchy-power-profiles-daemon` 0.30-7 applies its `performance` profile on AC to Apple Silicon, so the CPUs idle at their top clock and idle power on AC is about 10.5 W (MEASURED 2026-11-09). This is the stock default, not a J604 change.
7. **Built-in panel defaults.** Stock Omarchy drives every output at 8 bits per channel and gives Apple Silicon displays Hyprland's EDID colour preset. On this Mac our `omarchy-mac` (2.12 and later) and `omarchy-settings-dev` 1.4 make the built-in panel 10-bit and Display P3 by default (MEASURED 2026-11-09); external monitors are left alone, and a `monitors.lua` setting still wins. Both changes are drafted for upstream (see `UPSTREAM.md`).
